# GitHub DOM selectors

> How the content script finds Pull Requests and Issues on github.com without breaking on every GitHub release.

GitHub renders pages with React and Turbo. Its CSS class names are **hashed** (for example `prc-Link-Link-9ZwDx`, `ListItems-module__...`) and change between releases. Treat the DOM as an unstable API and prefer stable signals.

- **DON'T** select by hashed or generated class names, or by element position (`div > div:nth-child(3)`).
- **DO** use, in this order of preference:
    1. **`href` patterns** on links: `/{owner}/{repo}/pull/{n}` and `/{owner}/{repo}/issues/{n}` (match the pathname, ignore query and hash). Owner, repo and number are parsed from the `href` by `parseItemUrl` in [link-target-parser.ts](../../src/content/services/link-target-parser.ts).
    2. **Semantic attributes**: `data-testid`, `data-component`, `role` and `aria-*` attributes.
    3. **Stable legacy hooks** that GitHub keeps for classic pages (`id^="issue_"`, `.search-title`, `.gh-header-title`, `.js-issue-title`). These are semantic names, not hashed ones.

## Page detection

[page-detector.ts](../../src/content/services/page-detector.ts) decides from the URL what to do (`PageKind`); on any other page nothing is injected and mutations are ignored.

| Kind          | Paths                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `List`        | Repo: `/{owner}/{repo}/pulls` and `/issues`, filters `assigned\|created_by\|mentioned\|review-requested/{user}`, and `/{owner}/{repo}/pulls/{user}`. Global: `/pulls`, `/issues` and the `assigned`, `created`, `mentioned`, `review-requested`, `recent-activity` tabs. Search: `/search?type=pullrequests` or `type=issues`. Repository Discussions and Actions: `/{owner}/{repo}/discussions`, `/discussions/categories/{slug}`, `/{owner}/{repo}/actions`, `/actions/workflows/{file}` |
| `PullRequest` | `/{owner}/{repo}/pull/{n}` including sub-tabs (`/files`, `/commits`, `/checks`)                                                                                                                                                                                                                                                                                                                                                                                                            |
| `Issue`       | `/{owner}/{repo}/issues/{n}`                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `Discussion`  | `/{owner}/{repo}/discussions/{n}`                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `WorkflowRun` | `/{owner}/{repo}/actions/runs/{id}` including sub-pages (`/job/{id}`, `/attempts/{n}`)                                                                                                                                                                                                                                                                                                                                                                                                     |
| `Unsupported` | everything else, for example `/{owner}/{repo}/issues/new`                                                                                                                                                                                                                                                                                                                                                                                                                                  |

List paths are deliberately restricted: do not widen them to `.*`, or pages such as `/issues/new` get scanned.

`PageKind.PullRequest` also covers the sub-tabs (the copy button stays there). `isWorkflowRunSummary(location)` is true only for `/{owner}/{repo}/actions/runs/{id}` and the summary of one attempt, `/attempts/{n}` (no `/job/...` or other sub-pages), the only workflow run pages where the keyboard shortcut works. `isPullRequestConversation(location)` in the same file is true only for `/{owner}/{repo}/pull/{n}` (optional trailing slash, no sub-path): the Conversation tab, the only Pull Request page where the keyboard shortcut works.

## What the scanner looks for

[button-injector.ts](../../src/content/services/button-injector.ts):

- **List rows**: title links `a[data-testid="listitem-title-link"]`, `issue-pr-title-link`, `issue-listitem-title-link`, `a[id^="issue_"][id$="_link"]` and search result titles (`[data-testid="results-list"] .search-title a[href]`). If none is found, the fallback is a `a[href*="/pull/"], a[href*="/issues/"]` link inside `main` / `[role="main"]` that parses as an exact item link and has no hash or query (comment links like `#issuecomment-1` and filter links are not titles). Links inside dialogs, tooltips, menus, popovers, hovercards and the extension's own UI are ignored. The button is inserted **after the heading that wraps the title link** (or after the link itself), so it never becomes part of the title text.
- **Detail pages**: the title header (`h1[data-component="PH_Title"]`, the new pull request layout's `h1[data-component="Heading"] > .markdown-title` (resolved to its `h1`), `[data-testid="issue-title"]`, `.gh-header-title`, `bdi.js-issue-title`), skipping sticky scroll headers that repeat the title. The button goes right **after the `#123` number element** and is vertically centered on its line. Placement depends on the header:

    - React PR header (also the new pull request layout on the Conversation and Commits tabs, where the visible `#123` is in a suffix span right after the `h1`): the number is in a wrapper next to the `h1` (outside the heading); the button is added last inside that wrapper (or right after the number when the wrapper is not flex), so it stays outside the `h1`.
    - Issue page: the number is in an inline-flex wrapper **inside** the `h1`, together with GitHub's "Edit issue title" pencil when signed in; the button goes last in that wrapper, after the pencil, using the wrapper's gap.
    - Classic header (for example PR `/files`): the number is a plain span inside the `h1`; the button follows it.

    On the Issue page and the classic header the button is inside the `h1` on purpose: the `h1` wraps long titles and is followed by page actions, so a sibling would sit at the far right and read as a page action. Trade-off: there the heading's accessible name includes the button label.

- **Titles** come from the link text (lists) or the header title element (detail pages). Fallbacks for detail pages when the header yields nothing: `document.title`, then `meta[property="og:title"]`, parsed with the `… · Pull Request #n · owner/repo` / `… · Issue #n · owner/repo` suffixes removed.
- **Canonical URL** is built from owner, repo and number: `https://github.com/{owner}/{repo}/pull/{n}` or `/issues/{n}`. Never copy `location.href` as is (it can include tabs such as `/files`, queries or hashes).
- **Titles are data** — `title` is raw text; escaping is done by `buildLinkPayload` in `@shared/services`, not in the DOM code.

## SPA navigation and rescans

GitHub navigates without full page loads (Turbo), and React re-renders list rows. [page-observer.ts](../../src/content/services/page-observer.ts):

- A **`MutationObserver` on `document.documentElement`** (Turbo replaces `document.body`, so observing the body is not enough), `childList` + `subtree`.
- **Debounce 150 ms, at most 500 ms** of postponing while the DOM keeps changing.
- Also rescans on `turbo:load`, `turbo:render`, `popstate` and, where available (Chromium), the Navigation API `navigatesuccess` event.
- Mutations on unsupported pages are ignored (cheap observer) **unless the URL changed** since the last notification, so navigating from an unsupported page to a supported one still triggers a scan.
- **The extension's own changes are ignored**: a batch in which every record is inside a `[data-hyperfriend]` element (tooltip text, live region, toast, icon swaps) or only adds such elements schedules no rescan. A removed `[data-hyperfriend]` element still counts (GitHub's re-render may have dropped a button that must come back).
- A scan is cheap and **idempotent**; the initial scan runs after the config has loaded.
- **Wait for hydration** ([hydration-guard.ts](../../src/content/services/hydration-guard.ts)): nothing is injected into a server-rendered React root (`react-app` / `react-partial` with `data-ssr="true"`) until GitHub marks it with class `loaded`. A node added before hydration makes React's hydration fail, React renders the whole root again on the client and our button disappears for a moment (a click in that gap does nothing). The guard asks the page observer for a (debounced) rescan when the class appears, or after 10 s if it never does. Every injector checks `hydration.isPending(element)` before changing anything inside a React root. Page snapshots keep `class="loaded"`; the issue page spec removes it to test the wait.

## Author avatars

[avatar-injector.ts](../../src/content/services/avatar-injector.ts) adds a small author avatar to **Pull Request list rows** (list pages only). It is not added to Issue lists or search results (their rows have no author filter link).

- **Author link**: `a[data-testid="author-filter-link"]` inside the row (`li` or `[role="listitem"]`), and the row's title link `a[data-testid="listitem-title-link"]` must point to a Pull Request.
- **Login**: taken from the `author:` filter in the link's `q` query parameter (the visible text can be a display name such as "Jane Doe (jdoe)"), otherwise from the link text. It must look like a login (`[\w-]+`, optionally `[bot]`); anything else is skipped.
- **Skipped** when GitHub already renders an avatar in that place (`[data-component="Avatar"]`, `img.avatar`, for example Copilot rows), when the login failed to load before, or when an avatar is already there. Our avatar is also **removed** if GitHub renders its own avatar in the same row later (for example after hydration).
- **Element**: `img[data-hyperfriend="avatar"]` with `data-login`, inserted right before the author link; `alt=""`, `aria-hidden="true"`, `loading="lazy"`, 16×16, round ([avatar.css](../../src/content/styles/avatar.css), Primer-like 1 px ring from `--avatar-borderColor`). Source: `https://avatars.githubusercontent.com/{login}?size=32` (GitHub's own CDN; do not use other hosts).
- **Cleanup**: an avatar whose next sibling is no longer the author link of the same login is removed on the next scan; on a load error the avatar is removed and the login is not retried (no request loops).
- It is idempotent like the button: it runs in the same scan and never touches GitHub's own elements.

Avatars follow `display.authorAvatars` (config, popup tab General). The scan in `content.ts` skips avatar injection when it is `false` and calls `AvatarInjector.removeAll()` (removes every `img[data-hyperfriend="avatar"]`) so they disappear at once; turning it back on lets the next scan add them again. Config changes reach the scan through `ConfigStore` (`configService.subscribe`).

## Quick filter bar

- **Where**: Pull Request lists only (`isPullRequestList` in `page-detector.ts`: `/OWNER/REPO/pulls`, its filter sub-paths, `/pulls` and its tabs; not Issue lists, not search results, which have their own search form). Host-agnostic, so it works on github.com, `*.ghe.com` and granted Enterprise Server domains.
- **Anchor**: the list's search box, `[role="search"]` that contains an `input` and sits inside `[data-component="PageLayout"], main, [role="main"], #js-repo-pjax-container` (the site header's search box is outside). In the React list it is `div[role="search"][aria-label="Pull requests"]` with the combobox `input#repo-pulls-dashboard-filter-input` (no `<form>`, no `name="q"`). Classic server-rendered lists: the `form` of `main input[name="q"]`. The bar `div[data-hyperfriend="filter-bar"]` (`role="group"`, `aria-label="Quick filters"`) is inserted as the next sibling of the anchor; no anchor means no bar. `hydration.isPending(anchor)` is checked first (the anchor is inside the repo's React root). The live smoke test (`tests/live/smoke.spec.ts`) checks the anchor on real github.com.
- **Search text**: the `q` parameter of the address; a list without `q` shows GitHub's default for that page in the search box (`is:pr state:open` on a repository list, something else on `/pulls`), so the service reads the box's value then, and treats a page with neither as unknown (the bar still renders; the sticky redirect does nothing). A chip builds `pathname + ?q=...` (other parameters kept, `page` dropped) and opens it (`openAddress` in `filter-service.ts`). **On a React list the address is changed in place** (`history.pushState`, or `replaceState` for the sticky redirect) and a `popstate` event is dispatched on `window`; GitHub's router follows it, so the list updates without a page load and the bar stays the same element at the same place (a page load removes the bar until the page is rendered again, and the list jumps). The content script's isolated world is enough: the event reaches the page's listeners. Soft opening needs a hydrated list (`react-app` root); before that, and on classic lists, the page is loaded the usual way (`location.assign` / `location.replace`). If the search box does not show the new search text within 2 s (nothing followed the address) and the address is still the same, the page is loaded the usual way as a safety net. Nothing is opened when the new text equals the old one, and on a page without a known text outside a repository list (such as `/pulls` before its box is read).
- **Sticky chips**: `FilterService.applyRemembered` checks **each address once** (`checkedHref`; a change of the settings or of the remembered state in another tab only refreshes the bar, it never reloads a page) and only after `FilterService.start()` (the config and the remembered state are loaded). When `applyRememberedState` returns tokens it calls `location.replace` with them (no history entry). The search text is read from the address; an empty `q` counts as missing, and then from the list's search box, but only when the box is hydrated and its text has `is:pr` (during a soft navigation it can still be the box of the previous page); otherwise the check is tried again on the next scan. A `sessionStorage` key (`hyperfriend-filter-redirect`, `{ target, at }`) stops a second redirect to the same target within 10 s, so GitHub rewriting the address without the tokens cannot make a loop. A click on the sticky Drafts chip writes the new state to `FilterStateStore` (`chrome.storage.local`, key `hyperfriend-filter-state`, `{ drafts }`, default `hide`) before it navigates. Changes made in another tab arrive through `storage.onChanged`.
- **Chips**: `resolveChips(filters)` (shared) builds the chips of the bar from `filters.chips` in order, from the catalog and from the user's custom chips (`filters.custom`), so the bar needs no knowledge of where a chip comes from. A chip has a `colour` name; the button gets `data-colour` (not for `default`) and the CSS maps it to Primer variables (`--fgColor-success`, `-danger`, `-attention`, `-accent`, `-done`, `-severe`, `-muted`) through `--hyperfriend-chip-colour`: the icon uses it, and a chip with a colour uses it for the border and a `color-mix` soft background while `data-active` (the default chip keeps the accent look). The signature of the chip list (id, icon, colour) decides when the buttons are rebuilt. Custom names are written with `textContent`.
- **Element rules**: every chip is a `<button type="button">` with an inline Octicon (`FILTER_ICONS` in [octicons.ts](../../src/content/icons/octicons.ts): the 36 names of `CUSTOM_CHIP_ICONS`, `aria-hidden`, `currentColor` unless the chip has a colour) before its text span, and `data-active` when it filters the list; the on/off chips have `aria-pressed`, the Drafts chip (three states) has none and tells its state in its text (`Drafts: all`, `Drafts: hidden`, `Drafts: only`); text and attributes are written only when they change (the observer rescans on every mutation), the element is re-attached when Turbo replaced the body, and it is removed on `turbo:before-cache`. Styles ([filter-bar.css](../../src/content/styles/filter-bar.css)) use Primer variables with light fallbacks.
- **Tests**: the e2e router serves a filtered list (`/OWNER/REPO/pulls?q=...`) from the snapshot of the same list (`filteredListSnapshot` in `tests/e2e/fixtures/github.ts`), because a chip opens such addresses. The cross-repo `/pulls` has no snapshot (it needs a sign-in): the code covers its path and its default search text, and it is a manual check.

## Keyboard shortcuts

[shortcut-service.ts](../../src/content/services/shortcut-service.ts) registers **one `keydown` listener on `document` in the capture phase**, started after the config has loaded. Handlers live in [src/content/shortcut/](../../src/content/shortcut/): the `ShortcutHandler` interface (`type`, `isAvailable(kind, location)`, `handle(event)`) and one class per `ShortcutType`, registered in `content.ts`. The key combination is data (`config.shortcuts[type]`, read from `ConfigStore`), not part of the handler.

- **Matching**: by `KeyboardEvent.code` plus the exact modifier set (`matchesShortcut`), so it works with any keyboard layout. Only enabled bindings match.
- **Skipped** (the event is left untouched, no `preventDefault`): `event.repeat`, `event.isComposing`, `event.defaultPrevented`, a target or focused element (also inside open shadow roots) that is editable (`input`, `textarea`, `select`, `[contenteditable]` not `false`, `[role="textbox"]`, `[role="combobox"]`, `[role="searchbox"]`), an open modal dialog (`dialog[open]`, `[role="dialog"][aria-modal="true"]`, when rendered), a shortcut whose `isAvailable` is false for the current page, and any key press that matches nothing. Availability is evaluated on every key press (GitHub navigates without page loads).
- **On a match**: `preventDefault()` + `stopPropagation()`, then `handle(event)` **synchronously** (the clipboard write must start inside the `keydown` task to keep user activation).
- **Copy link** ([copy-link-shortcut-handler.ts](../../src/content/shortcut/copy-link-shortcut-handler.ts)): available on `PageKind.Issue`, `PageKind.Discussion`, the workflow run summary page (`isWorkflowRunSummary`) and on the Pull Request Conversation tab (`isPullRequestConversation`), not on `/files`, `/commits`, `/checks`. It reuses the detail title button (`ButtonInjector.getTitleButton()`, `CopyButton.copy()`), so the template, clipboard payload and feedback are identical to a click:
    - Button fully visible in the viewport (and not covered, e.g. by a sticky header): the usual "Copied!" / "Copy failed" tooltip.
    - Button out of view: `copy(false)` (the icon still changes, no tooltip) and a **toast**: "Link copied" / "Copy failed".
    - Button not injected yet: the target comes from `ButtonInjector.resolveDetailTarget()` (title header, then `document.title`) and `copyLink` is called directly, with the toast as feedback.
- **Toast** ([toast.ts](../../src/content/components/toast.ts), [toast.css](../../src/content/styles/toast.css)): one shared element `div.hyperfriend-toast` with **`data-hyperfriend="toast"`**, fixed at the bottom center of the viewport, Primer-like (colored icon block + text) using GitHub's CSS variables with light fallbacks, `aria-hidden` (the message is announced through the tooltip's live region), hides after about 2 s, animates only when `prefers-reduced-motion: no-preference`, hides on `turbo:visit` / `popstate` / `pagehide` and is removed on `turbo:before-cache`.
- **`aria-keyshortcuts`**: `ButtonInjector` sets it on the **detail page title button** (value from `ShortcutService.getAriaKeyShortcuts`, e.g. `Shift+C`) while the shortcut is enabled and available on the page, and removes it otherwise; it is refreshed on every scan, so config changes apply. The tooltip text does **not** mention the shortcut (do not add a hint to it).

## Discussions and workflow runs

Observed on github.com in 2026-10 (signed out); the e2e snapshots (`discussion-list`, `discussion`, `run-list`, `run`) hold the markup the tests run on.

- **Discussion list** (classic Rails list): title link `a.markdown-title[href*="/discussions/"]` in `li.Box-row` (the `data-hovercard-type="discussion"` attribute exists in some renderings only, so it is not used), and the pinned discussion `a.discussion-title` in `discussion-spotlight-container`. The comment-count link of a row has the same `href` but no `markdown-title` class. A row's author and category are the links with `aria-label="<login> (author)"` and `aria-label="<name> (category)"`.
- **Button placement in Discussion rows**: the title heading (`h3`) is a block, so the button is inserted right after the title **link inside the heading** (not after the heading, which put it on a line of its own); it sits next to the title and wraps with it. `getListReference` returns the link for Discussion title links; Pull Request, Issue and run rows still get the button after the heading.
- **Discussion page**: the classic issue header (`h1.gh-header-title` with `.js-issue-title.markdown-title` and `.gh-header-number`); author and category are links in the element after the heading (`.gh-header-title ~ * a[data-hovercard-type="user"]`, `a[href*="/discussions/categories/"]`). `document.title` is `<title> · owner/repo · Discussion #<n> · GitHub`.
- **Workflow run list** (`/actions`, React list view): the row is a `li` whose `aria-label` is `<status>: Run <n> of <workflow>. <title>` (the title part is missing for a run whose name is the workflow's, e.g. a scheduled run: the label then ends with the period after the workflow); the title link is `[data-listview-item-title-container] a[href*="/actions/runs/{id}"]` (an absolute URL). `readRunRow` reads the run number, workflow and status from that label. The branch is the row's `[data-component="BranchName"]`.
- **Workflow run page**: `h1.PageHeader-title` with `.markdown-title` (the run name) and a `.color-fg-muted` span `#<run number>`; the workflow is `.PageHeader-parentLink-label`, the status is the `aria-label` of the `svg` in `.actions-workflow-runs-status` (e.g. `completed successfully: `), the branch is `a.branch-name`. `document.title` is `<run name> · owner/repo@<sha> · GitHub` (no run number).
- **Identity**: the URL has the run **id** (`/actions/runs/39798109963`), the page shows the run **number** (`#20481`, per workflow). `parseItemUrl` returns the id as `number`; `parseListLink` / `parseDetailPage` replace it with the run number read from the page (the id when the page does not show one). The canonical URL is `https://github.com/{owner}/{repo}/actions/runs/{id}`, without attempts or jobs. Run numbers repeat across workflows, so the button's accessible name includes the workflow (`Copy link to workflow run CI #20481`) in lists; the run page has no stale-number check, because the URL id can not confirm the header number.

## Placeholder data

[link-metadata-parser.ts](../../src/content/services/link-metadata-parser.ts) reads the optional details of a target for the template placeholders. It runs only when a link is copied (`TargetResolver(withMetadata = true)` from `CopyButton.copy()` and `ButtonInjector.resolveDetailTarget()`), never during scans, labels or tooltips. Fields the page does not show are left out of the target (the placeholder then renders empty).

- **List rows** (`readListMetadata`, row = `li` or `[role="listitem"]` around the title link): author from `[data-testid="author-filter-link"]` (aria-label `Filter by author <login>`, else the `data-hovercard-url` `/users/<login>/hovercard`, else the text); state from the aria-label of a row icon `svg[data-component="Octicon"][aria-label]` (`Open pull request`, `Draft pull request`, `Closed`, ...); labels from `button[aria-label^="Filter by label "]` and classic `a.IssueLabel[data-name]`. Search results are not React list rows and give nothing.
- **Detail pages** (`readDetailMetadata(type, canonicalUrl, confirmed)`): author from `meta[property="og:author:username"]`, used only when `og:url` is the item's URL (the head can be stale after a soft navigation), else from the classic header link `.gh-header-meta a.author` (the Files and Commits tabs have no `og:author`); state from `[data-component="StateLabel"][data-status]` (`issueOpened`, `pullClosed`, `draft`, ...) or the classic `.State[title^="Status: "]`; labels from `.js-issue-labels a[data-name]` or `[data-testid="issue-labels"] a`; assignees from `[data-channel-event-name="assignees_updated"] [data-assignee-name]` (the reviewers block uses the same attribute but another event name) or profile links (`/login`, same site, a valid login) in `[data-testid="sidebar-assignees-section"]`; milestone from a `/milestone/` link in the milestone sidebar section; branches (pull requests) from the first two `[data-component="BranchName"]` elements (base, then head), else the first two `.gh-header-meta .commit-ref` of the classic header.
- **Stale pages**: `parseDetailPage` passes `confirmed` = the header's `#number` equals the URL's number. When it is not confirmed (after a soft navigation, or no number element) only the author from the URL-checked meta tags is read, so a link never carries the previous item's state, labels or branches.
- State words are matched at the start of the text (after dropping `Status: ` and a leading `issue` / `pull`), in the order `draft`, `merged`, `closed`, `open`.
- Markup coverage: list rows, the PR header (React and classic) and the labels of PR 9713 come from the snapshots; the React issue sidebar (labels, assignees, milestone) and the classic assignee and milestone blocks are tested with markup injected into the snapshot, because the snapshots show none. After a GitHub markup change, check them on a live item that has labels, an assignee and a milestone.
- The e2e tests check the pull request and issue pages against literals in the specs (the `beforeAll` of each spec compares them with `index.json`), and the lists against the details `capture-pages.mjs` records per row (`requireState` makes the capture fail when no row shows a state).

## Selecting several rows

[selection-service.ts](../../src/content/services/selection-service.ts), [selection-bar.ts](../../src/content/components/selection-bar.ts), [selection-bar.css](../../src/content/styles/selection-bar.css).

- **Shift+click** on a **row** button (`CopyButtonPlacement.Row`, the only one with `onSelect`) calls `SelectionService.toggle` instead of copying (`preventDefault` + `stopPropagation` as for a click; a Shift+`mousedown` is prevented too, so the page's text selection is not extended). Title buttons of detail pages ignore Shift. `Shift+Enter` on a focused button arrives as a click with `shiftKey`, so it needs no extra code.
- **State**: a `Set` of canonical item **URLs** (not buttons: React may replace a row, and the new button of the same item shows the selection again; a pinned discussion that is also a row is one item) and the page key (`pathname + search`) of the first selection. `ButtonInjector.scan()` calls `SelectionService.sync(rowButtons)` **after** the scan: it clears everything when the page key changed or the page is no list, re-marks the current buttons, and drops the items that no row button shows any more.
- **Selected look and meaning**: `data-selected` on the button (accent color, background and an inset ring, plus a `Highlight` outline in forced-colors mode); `aria-description` on every row button (`Shift+click to select several` / `Selected. Shift+click to remove`; the `aria-label` stays `Copy link to ...`); the tooltip hints the same. Changes are announced through the tooltip's live region (`Added to the selection, 2 selected`; the first one adds where the bar is).
- **Bar**: one `div[data-hyperfriend="selection-bar"]` (`role="region"`, `aria-label="Selected links"`), fixed at the bottom center (`z-index: 90`, below GitHub's dialogs), with a count text and two real buttons, `Copy link(s)` and `Clear`. It is re-attached when Turbo replaces `document.body` and removed on `turbo:before-cache`. **The bar writes text and attributes only when they change**: the page observer rescans on every childList mutation, so an unconditional write would rescan in a loop and replace the result message. "Copy" runs `copyLinks` synchronously inside the click, with one button per selected item in page order and `getTarget()` (details included); the bar then shows `N links copied` (or `Copy failed`, which keeps the selection) and clears 1.5 s later. While a result is shown the Copy button is `aria-disabled` (not `disabled`, so a focused button keeps its focus) and rescans do not touch the text. When the bar goes away with the focus inside it, the focus moves to the last toggled row button.
- **Escape** clears the selection (listener on `document`, **bubble** phase, after GitHub's own handlers) unless the event was already handled, is part of IME composition, the target or the focused element is a text field or a composite widget (`isKeyboardTarget`), a modal dialog is rendered (`isModalDialogOpen`) or a popover is open (`:popover-open`); the helpers are the ones of the keyboard shortcut service.

## Idempotent markers

- The injected button has **`data-hyperfriend="copy-button"`** (`data-selected` while it is part of a selection); avatars have **`data-hyperfriend="avatar"`**, the tooltip, live region and toast `tooltip`, `live-region` and `toast`.
- **`data-hyperfriend-processed`** is set on the host that got a button: the title link in lists, the title header on detail pages.
- Before inserting, the injector checks the real next sibling (not only a marker), because React may recreate nodes; an existing button is only updated (its label follows the current title and templates). A button left by an older instance of the script is replaced. Stale title buttons on detail pages are removed, and row buttons whose title link was replaced or moved (React may recreate only the link) are removed at the start of every scan and re-created.

## Styling and behavior

- [copy-button.css](../../src/content/styles/copy-button.css) styles the button like Primer `IconButton variant="invisible"`: 24×24 in list rows, 32×32 on detail headers, the icon stays muted on hover. Colors come from GitHub's Primer CSS variables that exist on the page (for example `--fgColor-muted`, `--bgColor-neutral-muted`, `--borderColor-default`) with light-theme fallbacks, so the button follows GitHub's light and dark themes.
- **Tooltip**: there is no native `title`. One shared GitHub-style tooltip (`.hyperfriend-tooltip`, `data-hyperfriend="tooltip"`, styles in [tooltip.css](../../src/content/styles/tooltip.css), logic in [tooltip.ts](../../src/content/components/tooltip.ts)) shows "Copy link to pull request" / "Copy link to issue" on hover and focus, then "Copied!" / "Copy failed" for 1.5 s. It is `aria-hidden`; a hidden polite live region (`data-hyperfriend="live-region"`) announces the result. Both are created on supported pages and removed on `turbo:before-cache` so they do not end up in Turbo snapshots.
- Icons are inline SVG (Octicons `copy`, `check`, `x`, 16 px) in [octicons.ts](../../src/content/icons/octicons.ts). Do not pull React into the content script.
- The click handler calls `copyLink` synchronously (no `await` before it) with the config from `ConfigStore`. States: copy icon, then "Copied!" (check icon) or "Copy failed" (x icon) for 1.5 s. `aria-label` is `Copy link to pull request #12` / `Copy link to issue #7` (not the rendered template text), so buttons in a list have distinct names.
