Release `$ARGUMENTS` in two phases and track their steps as a checklist. **Phase 2 changes GitHub and starts only after the user confirms in chat**; a confirmation for one release never covers the next one.

## Versioning

- Semantic versioning: `patch` for fixes only, `minor` for new features that stay compatible (stored settings and settings files keep working), `major` for breaking changes (for example a settings file older versions cannot import, or a removed feature).
- No argument: propose the version from the changes since the last tag (`git log <last-tag>..HEAD`) and ask the user before changing files.
- `public/manifest.json` is the source of truth. [set-version.sh](../../../.husky/set-version.sh) copies the version to `package.json` and `public/manifest.firefox.json`; [tag-releases.sh](../../../scripts/tag-releases.sh) finds the release commit by that version.

## Phase 1: prepare (local only)

1. **State**: on `master`, `git fetch origin` and confirm `master` is not behind `origin/master`. Only changes that belong to the release are in the working tree.
2. **Version**: set `"version"` in `public/manifest.json`, run `./.husky/set-version.sh`, then `npm install --package-lock-only --ignore-scripts`. `git diff package-lock.json` must show only the two root `version` fields.
3. **Release notes**: `RELEASE_NOTES.md` has a `## x.y.z` section at the top (newest first; the tag script reads these headings). User-visible changes are also in `README.md` and `LISTING.md` (see [docs-and-ci.md](../../rules/docs-and-ci.md)). Write in English and add no attribution lines.
4. **Store assets**: if the popup, the copy button or the branding changed, run `/store-assets` and commit the new images with the release.
5. **Checks**: run `/verify`; every step must pass. Then run `npm run test:live` (smoke test against real github.com; it needs network) and report its result in step 7. A failure there means GitHub changed its markup, not that the build is broken: tell the user and let them decide.
6. **Commit**: one commit `Release x.y.z: <summary>` with a short bullet list of changes, no co-author or "generated by" lines (git asks for confirmation). The Husky pre-commit hook formats, rebuilds both targets and writes `hyperfriend-build-chrome_<date-time>_x.y.z.zip` and `hyperfriend-build-firefox_<date-time>_x.y.z.zip` to the repository root (gitignored).
7. **Stop and report**: the commit hash, the two zip paths, what was verified, and the `test:live` result. Ask the user to test the build locally and to confirm the push.

## Phase 2: publish (after the user confirms)

1. **Push**: `git push origin master` (git asks for confirmation).
2. **CI**: find the run of the release commit (`gh run list -R borbiuk/hyperfriend --commit <sha>`; it can take a few seconds to appear) and wait for it with `gh run watch <id> -R borbiuk/hyperfriend --exit-status`. Both jobs of `build.yml` must pass: `build` (all Node versions) and `e2e`. On failure stop and report the failing job; the `e2e` job uploads the artifact `playwright-report-e2e`.
3. **Tag**: `DRY_RUN=1 ./scripts/tag-releases.sh` must report `Would tag x.y.z at <release commit>` and no other `Would tag` line (the script tags every `RELEASE_NOTES.md` version that has no tag yet). It picks the newest commit that changed `public/manifest.json` and has that version, so if the version was set in an earlier commit than the one that should be tagged, tag by hand: `git tag -a x.y.z <sha> -m "Release x.y.z"`. Otherwise run `./scripts/tag-releases.sh`. Check with `git cat-file -p x.y.z` (annotated, tagger is the maintainer), then `git push origin refs/tags/x.y.z`.
4. **Assets**: copy the newest root zips of this version to a scratch directory as `hyperfriend-chrome-x.y.z.zip` and `hyperfriend-firefox-x.y.z.zip`. Check `"version"` inside each with `unzip -p <zip> manifest.json`.
5. **Notes**: the body of the `## x.y.z` section from `RELEASE_NOTES.md`, then an `### Install` block (the two zip names; to try a build without a store, unzip it and load it as an unpacked extension in Chrome via `chrome://extensions` → Developer mode → Load unpacked, or in Firefox via `about:debugging` → This Firefox → Load Temporary Add-on → `manifest.json`), then `**Full changelog:** https://github.com/borbiuk/hyperfriend/compare/<previous tag>...x.y.z`. Write it to a scratch file, not the repository.
6. **GitHub Release**: `gh` must act as an account with write access to `borbiuk/hyperfriend`. If several accounts are logged in, `gh auth switch` to it for this step only and switch back afterwards. Run `gh release create x.y.z -R borbiuk/hyperfriend --verify-tag --latest --title "Hyperfriend x.y.z" --notes-file <notes> <chrome zip> <firefox zip>`.
7. **Verify**: `gh release view x.y.z -R borbiuk/hyperfriend` lists both assets and `gh api repos/borbiuk/hyperfriend/releases/latest -q .tag_name` returns `x.y.z`.
8. **Report**: commit, CI run URL, tag, release URL, and for the manual store upload the root zip paths plus the store images that changed (see [design/store/README.md](../../../design/store/README.md)). Store publication is done by the maintainer.
